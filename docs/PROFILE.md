# Shielded Bitcoin implementation profile (draft v0.2)

Status: **draft, not frozen**. Every choice here is subject to change until the
first trusted setup is run. After that, the profile is versioned and changes
require a new protocol version byte.

This document fixes every parameter that the paper
[*Shielded Bitcoin: Private Transfers on the Bitcoin L1*](https://www.allocinit.xyz/uploads/shielded-bitcoin.pdf)
(Shikhelman, Komarov, Moskvin, 24 Sep 2026) leaves to an "implementation
profile" (paper §A, §22.1). Section numbers below refer to the paper.
Where this profile departs from a recommended default of the paper, the
departure is listed in §10 with its reason.

Terminology follows the paper: `v` value, `d` diversifier, `rseed` note seed,
`rho`, `sk_eph`, `pk_eph`, `pk_d`, `G_d`, `nf`, `pos`, `h_body`, `leaf`,
`r_anchor`, `h_anchor`, `ct_note`, `ct_out`, `W`, `K_min`, `K_wallet`.

---

## 1. Algebraic setting

| Object | Choice |
|---|---|
| Proof system | Groth16 (§A.1) |
| Pairing curve | BLS12-381 |
| SNARK scalar field | `Fr` = BLS12-381 scalar field, `q = 0x73eda753299d7d483339d80809a1d80553bda402fffe5bfeffffffff00000001` (255 bits) |
| Embedded curve | Jubjub: twisted Edwards `-x^2 + y^2 = 1 + d x^2 y^2` over `Fr`, `d = -(10240/10241)` |
| Jubjub subgroup order | `r_J = 0x0e7db4ea6533afa906673b0101343b00a6682093ccc81082d0970e5ed6f72cb7` (cofactor 8) |
| Jubjub generator `G` | The Zcash Sapling spending-key base `G` is **not** used. `G` is defined as `DiversifyHash(0^11)` restricted to the subgroup, see §4.2. (Only `G_d` bases are used by the protocol; a fixed generator is needed only for test vectors.) |
| Proof encoding | 192 bytes: `A` (G1, 48 bytes compressed) `‖ B` (G2, 96 bytes) `‖ C` (G1, 48 bytes), arkworks canonical compressed encoding |

All field elements on the wire are **32-byte little-endian canonical** encodings
(value `< q`, else reject).

All Jubjub points on the wire are **32-byte compressed**: `y` as 32-byte LE
with bit 255 set to the least significant bit of `x` (Zcash convention).
Decoding rejects `y >= q`, non-square `x^2`, and points outside the
prime-order subgroup.

## 2. Hash functions

### 2.1 Poseidon (in-circuit hash)

One Poseidon permutation instance is used for every in-circuit hash:

| Parameter | Value |
|---|---|
| Field | `Fr` (BLS12-381 scalar field) |
| Width `t` | 3 (rate 2, capacity 1) |
| S-box | `x^5` |
| Full rounds `R_F` | 8 |
| Partial rounds `R_P` | 57 |
| Round constants, MDS | Generated by the Grain-LFSR procedure of the Poseidon reference implementation (`generate_params_poseidon.sage`, field=1, sbox=0, n=255, t=3, R_F=8, R_P=57, prime=q). The constants are pinned in `sb-primitives` and their SHA-256 is a test vector. |

Hash mode `PH(tag, x_1, …, x_n)` ("Poseidon hash with tag"):

```
elems  = [tag, x_1, …, x_n]              # tag first, then inputs
pad elems with 0 to even length
state  = [n + 1, 0, 0]                    # capacity = number of real elements incl. tag
for each pair (a, b) in elems:
    state[1] += a ; state[2] += b
    state = Perm(state)
return state[1]
```

Every call site has a distinct `tag` and a fixed `n`, so zero padding is
unambiguous. Tags are `Fr` elements: `tag = LE_bytes_mod_q(ASCII string)`.

| Tag name | ASCII string | Used for |
|---|---|---|
| `T_NODE` | `"sb/v1/node"` | Merkle node `PH(T_NODE, left, right)` |
| `T_LEAF` | `"sb/v1/leaf"` | Note leaf (§5.3) |
| `T_NF` | `"sb/v1/nf"` | Nullifier (§5.4) |
| `T_RHO` | `"sb/v1/rho"` | `rho = PH(T_RHO, rseed)` |
| `T_EPH` | `"sb/v1/eph"` | `sk_eph = Scalar250(PH(T_EPH, rseed))` |
| `T_SKNF` | `"sb/v1/sknf"` | `sk_nf = PH(T_SKNF, sk_spend)` |
| `T_VKIN` | `"sb/v1/vkin"` | `vk_in = PH(T_VKIN, sk_spend)` |
| `T_VIEW` | `"sb/v1/view"` | `sk_view = Scalar250(PH(T_VIEW, vk_in))` |
| `T_DIV` | `"sb/v1/div"` | DiversifyHash (§4.2) |
| `T_KDF` | `"sb/v1/kdf"` | Note key `k = PH(T_KDF, ss.x, ss.y, pk_eph.x, pk_eph.y)` |
| `T_STREAM` | `"sb/v1/stream"` | Keystream `PH(T_STREAM, k, i)` |
| `T_MAC` | `"sb/v1/mac"` | Note tag `PH(T_MAC, k, c_0, c_1)` |

`Scalar250(f)` = the integer formed by the low 250 bits of the canonical
LE encoding of `f`, used as a Jubjub scalar. `2^250 < r_J`, so no reduction
occurs and the same bits drive the in-circuit scalar multiplication.

### 2.2 Byte-oriented hashes (off-circuit only)

| Function | Choice |
|---|---|
| `H_body` | `SHA-256(const_salt ‖ body_bytes)`, then **clear bits 253..255** of the LE value, interpreted as `Fr`. (253-bit collision resistance; `h_body` is only ever an opaque public input.) |
| Recovery binding digest | `SHA-256(M as 1 byte ‖ pk_eph_0 ‖ … ‖ pk_eph_{M-1} ‖ ct_note_0 ‖ … ‖ ct_note_{M-1})` (wire encodings) |
| HKDF | HKDF-SHA256 (RFC 5869) |

## 3. Keys and addresses (§6, Table 1)

Wallet seed: 32 uniformly random bytes (§A.2).

| Key | Derivation |
|---|---|
| `sk_master` | `HKDF-SHA256(ikm = seed, salt = "", info = "sb/v1/master", L = 32)` |
| `sk_spend` | `LE_int(HKDF-SHA256(ikm = sk_master, salt = "", info = "sb/v1/spend", L = 64)) mod r_J` (Jubjub scalar) |
| `sk_spend_ser` | 32-byte LE canonical encoding of `sk_spend` |
| `sk_spend` as `Fr` | `LE_int(sk_spend_ser)` (`< r_J < q`, no reduction) — this is the circuit witness |
| `vk_out` | `HKDF-SHA256(ikm = sk_master, salt = "", info = "sb/v1/out", L = 32)` |
| `sk_nf` | `PH(T_SKNF, sk_spend)` ∈ `Fr` (derived in circuit) |
| `vk_in` | `PH(T_VKIN, sk_spend)` ∈ `Fr` (derived in circuit) |
| `sk_view` | `Scalar250(PH(T_VIEW, vk_in))` (derived in circuit) |

Diversified address for diversifier `d` (11 bytes, §A.2):

```
G_d  = DiversifyHash(d)          # §4.2, may fail → d is invalid, pick the next d
pk_d = [sk_view] G_d
addr = (d, pk_d)
```

Diversifier selection: `d_i = HKDF-SHA256(ikm = vk_in_bytes, salt = "", info = "sb/v1/diversifier" ‖ LE64(i), L = 11)`
for `i = 0, 1, 2, …`, skipping indices whose `G_d` is invalid (≈ 50 %).
`vk_in_bytes` is the 32-byte LE encoding of `vk_in`.

Address text encoding: bech32m, payload `d (11) ‖ pk_d (32)` = 43 bytes.
HRP: `sb` mainnet, `tsb` signet/testnet, `rsb` regtest.

Viewing-key export formats (for §7 disclosure): `vk_in` as `sbvk1…` (bech32m
over 32 bytes), `vk_out` as `sbovk1…`.

## 4. Group operations

### 4.1 Subgroup checks

Every point that enters the circuit as a recipient key (`pk_d` of an output)
is witnessed as `pk_d_root` and the circuit uses `pk_d = [8] pk_d_root`,
which forces `pk_d` into the prime-order subgroup. Natively, parsers check
`[r_J] P = O` and `P ≠ O`.

### 4.2 DiversifyHash

```
DiversifyHash(d):
    y  = PH(T_DIV, LE_int(d))                       # d as an 88-bit field element
    u  = (y^2 - 1) / (d_J * y^2 + 1)                # candidate x^2 (d_J = Jubjub d)
    if u is not a square in Fr: return INVALID
    x  = sqrt(u) with x even (LSB = 0)              # canonical sign
    P  = [8] (x, y)                                 # clear cofactor
    if P = O: return INVALID
    return P
```

In circuit the prover witnesses `x`, the circuit checks the curve equation,
`x` even (via bit decomposition), and performs the three doublings. Roughly
half of all diversifiers are invalid; wallets skip them (same behaviour as
Sapling). Invalid-`d` addresses cannot be encoded.

Rationale for not using a deterministic map (Elligator 2): equal security,
one third of the constraints, far simpler to get byte-identical across
implementations.

## 5. Notes

### 5.1 Plaintext

`pt_note = (v, d, rseed)`:

| Field | Type | Encoding in `Fr` |
|---|---|---|
| `v` | u64 satoshis, `v < 2^64` (range-checked in circuit) | — |
| `d` | 11 bytes | — |
| `rseed` | uniformly random `Fr` element | itself |
| `m_0` | packed `v + 2^64 · LE_int(d)` (152 bits) | `Fr` |
| `m_1` | `rseed` | `Fr` |

Per-note derived values: `rho = PH(T_RHO, rseed)`,
`sk_eph = Scalar250(PH(T_EPH, rseed))`, `pk_eph = [sk_eph] G_d`.

### 5.2 Recipient channel (§12.1)

```
ss  = [sk_eph] pk_d                                 # ECDH, Jubjub point
k   = PH(T_KDF, ss.x, ss.y, pk_eph.x, pk_eph.y)
c_0 = m_0 + PH(T_STREAM, k, 0)
c_1 = m_1 + PH(T_STREAM, k, 1)
tag = PH(T_MAC, k, c_0, c_1)
ct_note = c_0 ‖ c_1 ‖ tag                           # 96 bytes on the wire
```

Decryption (recipient): `ss = [sk_view] pk_eph`, recompute `k`, check `tag`,
unmask, then unpack `m_0` (reject if `v ≥ 2^64` or the `d` part exceeds 88 bits).
Then apply the §16.1 checks: `pk_eph == [sk_eph(rseed)] DiversifyHash(d)`, `d` maps
to a local receive path with that `pk_d`, and the recomputed leaf equals the
replay-assigned leaf.

Properties (§A.1, A6): the MAC commits to `k`, `k` commits to `ss` and
`pk_eph` (both coordinates), so one ciphertext opens under exactly one
recipient key and to exactly one plaintext (committing); ciphertexts are
pseudorandom under an unknown `k` (key private).

### 5.3 Leaf (§9)

```
leaf = PH(T_LEAF, const_salt, h_body, j, pk_eph.x, pk_eph.y, c_0, c_1, tag, h_aux)
```

`j` = output index in the creating envelope. `h_aux = 0` (`aux_null`, §22.5),
not serialised. `const_salt` is the deployment constant of §9.

### 5.4 Nullifier (§9)

```
nf = PH(T_NF, sk_nf, rho, pos)
```

`pos` = replay-assigned leaf position as an `Fr` element.

## 6. Note tree (§8)

Append-only Merkle tree, depth **32**, Poseidon nodes
`PH(T_NODE, left, right)`, empty leaf value `0`, empty subtree roots
`E_0 = 0`, `E_{i+1} = PH(T_NODE, E_i, E_i)`. Leaves are appended left to
right; `pos` is the zero-based index. Roots `R[h]` are recorded per Bitcoin
block height after the whole block has been replayed (§8, §15).

## 7. Transfer envelope (§A.3, §A.5)

Fixed arity for protocol version 1: **N = 2 inputs, M = 2 outputs**. Smaller
transfers are padded with dummy notes (§8.2 below). Any other arity is invalid.

### 7.1 Body bytes

| # | Field | Bytes | Encoding |
|---|---|---|---|
| 0 | `magic` | 3 | ASCII `"btc"` |
| 1 | `version` | 1 | `0x01` |
| 2 | `kind` | 1 | `0x01` transfer |
| 3 | `reserved` | 1 | `0x00`, must be zero |
| 4 | `h_anchor` | 4 | u32 LE block height |
| 5 | `input_count` | 1 | CompactSize, value `2` |
| 6 | `output_count` | 1 | CompactSize, value `2` |
| 7 | `nf[0..2]` | 2 × 32 | `Fr` LE canonical |
| 8 | `pk_eph[0..2]` | 2 × 32 | compressed Jubjub |
| 9 | `ct_note[0..2]` | 2 × 96 | `c_0 ‖ c_1 ‖ tag`, each `Fr` LE canonical |
| 10 | `ct_out` | 176 | §7.3 |
| — | **body total** | **508** | |
| 11 | `proof` | 192 | Groth16 compressed |
| — | **envelope total** | **700** | |

A parser rejects: wrong magic/version/kind, non-zero reserved byte, counts
≠ 2, non-canonical CompactSize, any non-canonical field element or point,
trailing bytes, and any envelope whose re-serialisation differs from the
published bytes.

### 7.2 `h_body`

`h_body = H_body(const_salt ‖ body_bytes)` (§2.2). `const_salt` is a 32-byte
deployment constant (§9); its `Fr` embedding (LE, bits 253..255 cleared) is
the `const_salt` element in the leaf hash.

### 7.3 Sender-recovery channel `ct_out` (§12.2)

```
digest = SHA-256(0x02 ‖ pk_eph_0 ‖ pk_eph_1 ‖ ct_note_0 ‖ ct_note_1)   # §2.2
key    = HKDF-SHA256(ikm = vk_out, salt = digest, info = "sb/v1/ctout/key",   L = 32)
nonce  = HKDF-SHA256(ikm = vk_out, salt = digest, info = "sb/v1/ctout/nonce", L = 12)
pt     = 0^32 ‖ pk_d_0 (32, compressed) ‖ sk_eph_0 (32, LE) ‖ pk_d_1 ‖ sk_eph_1   # 160 bytes
ct_out = ChaCha20-Poly1305(key, nonce, aad = digest, pt)                         # 176 bytes
```

The 32 zero bytes are the padding fix that makes the AEAD key-committing
(§A.1): a decryptor rejects any plaintext whose first 32 bytes are not zero,
so one `ct_out` cannot open under two keys to two valid batches.

Sender-side recovery (§16.2) decrypts `ct_out`, then for each output derives
`ss = [sk_eph_j] pk_d_j`, decrypts `ct_note_j`, and applies the same checks as
the recipient. A wallet records a sent note only when at least one nullifier
of the envelope belongs to one of its own notes.

## 8. Transfer statement and circuit (§14, §B)

### 8.1 Public inputs (in this order)

```
x = [ const_salt,
      r_anchor,
      N (=2), M (=2),
      nf_0, nf_1,
      pk_eph_0.x, pk_eph_0.y, pk_eph_1.x, pk_eph_1.y,
      c_0^0, c_1^0, tag^0,  c_0^1, c_1^1, tag^1,
      h_body ]                                         # 17 Fr elements
```

`r_anchor = R[h_anchor]` is derived by replay, never serialised.
`const_salt` (its `Fr` embedding, §7.2) is a public input rather than a
circuit constant so that one trusted setup serves every deployment; the
indexer supplies its own deployment's value. The circuit also enforces
`N = M = 2` in-circuit.

### 8.2 Witness

```
sk_spend                                   # one Fr element for all inputs
for i in 0..2:  (v_i, d_i, rseed_i, h_body_create_i, j_i, pos_i, path_i[32])
for j in 0..2:  (v_j, d_j, rseed_j, pk_d_root_j)
```

The DiversifyHash gadget witnesses the even `x` for `y = PH(T_DIV, d)`
internally (it is a function of `d`, not independent witness data).
`pk_eph`, `ct_note` and the leaf of each input are re-derived in circuit,
never witnessed (§14.3). `v` is allocated as 64 bits and `d` as 88 bits
(range checks of block 6 and canonical `m_0` packing); `pos` as 32 bits. A **dummy input** has `v = 0`, a fresh random `rseed`, `pos = 0`,
an arbitrary path, and still publishes its (unique, random) nullifier;
the Merkle check is skipped exactly when `v = 0`. A **dummy output** is a
real zero-value note to one of the sender's own addresses.

### 8.3 Constraints (Appendix B blocks)

1. For each input: derive `rho`, `sk_eph`, `G_d = DiversifyHash(d)`, `sk_nf`,
   `vk_in`, `sk_view`, `pk_d = [sk_view] G_d`, `pk_eph = [sk_eph] G_d`,
   `ss = [sk_eph] pk_d`, `ct_note` per §5.2, `leaf` per §5.3.
2. Merkle root of `(leaf, pos, path)` equals `r_anchor` unless `v = 0`.
3. (Spend authorization is block 1's use of `sk_view` from `sk_spend`.)
4. `nf_i == PH(T_NF, sk_nf, rho_i, pos_i)` for the public `nf_i`.
5. For each output: `pk_d = [8] pk_d_root`, `G_d = DiversifyHash(d)`,
   `pk_eph`, `ss = [sk_eph] pk_d`, `ct_note` per §5.2; constrain equal to the
   public `pk_eph_j`, `ct_note_j`.
6. Every `v` is 64-bit range checked (bit decomposition).
7. `v_in_0 + v_in_1 == v_out_0 + v_out_1` (no overflow possible: 65 bits ≪ 255).
8. `h_body`, `N`, `M` are public inputs; each is multiplied into one trivial
   constraint so that no public input is left unconstrained in the R1CS.
   Replay recomputes `h_body` and `r_anchor` from the published envelope.

Expected size: ≈ 100 k R1CS constraints (to be measured).

### 8.4 Proving/verifying key

`params/transfer-v1.pk` and `params/transfer-v1.vk`. The deployment profile
(§9) pins `SHA-256(vk)`. Development deployments use a deterministic
**insecure** setup from a published seed (anyone can forge proofs); this is
printed loudly by every tool. A production deployment requires an MPC
ceremony, which is out of scope of this draft.

## 9. Deployment profile

A deployment is a JSON file (`deployments/<name>.json`):

```json
{
  "name": "signet-dev-1",
  "network": "signet",
  "activation_height": 0,
  "const_salt_hex": "…32 bytes…",
  "transfer_vk_sha256": "…",
  "setup": "insecure-seed:<hex>" | "ceremony:<url>",
  "window_w": 100,
  "k_min": 1,
  "initial_notes": []
}
```

`const_salt = SHA-256("sb/v1/const_salt/" ‖ name)` by convention, so
different deployments produce different `h_body` and leaves for the same
body and cannot be cross-replayed.

Anchor window (§A.6): `W = 100`, `K_min = 1`; replay in block `H` accepts
`H − 100 ≤ h_anchor ≤ H − 1`. Wallet default `K_wallet = 3`.

## 10. Publication carrier (§A.4)

One OP_RETURN output whose script is exactly `OP_RETURN <single minimal push of the envelope>`
(`OP_PUSHDATA2` for 700 bytes). A transaction is a **candidate** if exactly one
of its outputs is an OP_RETURN whose single push starts with `"btc" 0x01`.
A candidate with two such outputs, extra pushes, or a non-minimal push is
**rejected and logged** (it never mutates state). Witness data is ignored.
OP_RETURN outputs whose payload does not start with the magic are not part
of the envelope and never affect acceptance (deployment extensions may use
them, see `docs/BOUNDARY.md`).
Transactions in a block are processed in block order; blocks from
`activation_height` upward.

## 11. Replay acceptance order (§A.7, §15)

For each candidate envelope in block `H`:

1. parse canonically (§7.1), else reject;
2. recompute `h_body`;
3. check `H − W ≤ h_anchor ≤ H − K_min`, else reject;
4. `r_anchor = R[h_anchor]`;
5. nullifiers pairwise distinct and none in `N`, else reject;
6. verify the Groth16 proof for `x` (§8.1), else reject;
7. derive `leaf_0, leaf_1`, append to `T`, assign positions, insert nullifiers
   into `N`, append the event to `H`.

After the last transaction of block `H`: `R[H] = root(T)`. Reorganisation:
the indexer keeps a per-block checkpoint (leaf count, nullifiers added,
events) and rolls back to the fork point, then replays forward.

## 12. Departures from the paper's recommended defaults

| Paper | This profile | Why |
|---|---|---|
| `sk_nf`, `vk_in`, `sk_view` via HKDF-SHA256 (Table 1, eq. 1) | Poseidon (§3) | These three are derived **in circuit** (§9, §B block 3–4). HKDF-SHA256 in R1CS costs ≈ 700 k constraints; Poseidon ≈ 1 k. The paper's §A.1 explicitly leaves in-circuit gadgets to the profile. |
| `ct_note` 67 bytes (§A.4 estimate) | 96 bytes (3 × `Fr`) | Ciphertext/plaintext consistency must be proved in circuit (§12.1). A byte AEAD in R1CS is 30–160 k constraints per note; the Poseidon construction is ≈ 2 k. Envelope grows 610 → 700 bytes (with the 32-byte `ct_out` commitment pad). |
| Magic `"btc"` | same | — |
| DiversifyHash unspecified | §4.2 | — |
| Public statement listed as a tuple | identical, 16 `Fr` public inputs, no projection | — |

## 14. Out of scope of this profile (deployment layer)

* Peg-in / peg-out (PIPEs v2, §20.4, §22.3). Development deployments use a
  non-normative **mint** envelope kind (`0x02`) and a vault key; see
  `docs/BOUNDARY.md` when it exists.
* Fee funding and relayers (§20.5).
* Light-client verified sync (§22.2).
* Opt-in lineage attestations (§D).

# Variant A implementation profile: Halo 2 over Pasta (draft v0.1)

Status: **draft, not frozen**; the normative profile of variant A
(`VARIANT-A.md`), the paper's transfer protocol with a transparent proof
system. This document is a **delta to `PROFILE.md` v0.2**: every section
below names the section of `PROFILE.md` it replaces or amends, and
everything not mentioned is inherited unchanged. Paper section numbers
are the paper's. Variant A is a separate **family** (`VARIANT-A.md` §6):
its envelopes are invalid under the paper profile and vice versa, and no
interoperability is claimed.

What is in scope of v0.1: the transfer relation and its envelope, keys,
addresses, notes, the tree, replay acceptance, the deployment profile.
Out of scope until their own slices: the swap extension (`SWAP.md`), the
batch circuit and replay proofs (`REPLAY-PROOF.md`), the fee vault's
signature scheme (`FEE-VAULT.md`, unchanged in principle: it signs
`h_body` with BIP 340 and never touches the proof system).

---

## 1. Algebraic setting (replaces `PROFILE.md` §1)

| Object | Choice |
|---|---|
| Proof system | Halo 2: PLONKish arithmetization, inner-product-argument polynomial commitment, no trusted setup (`halo2_proofs` 0.3 semantics) |
| Circuit field | `Fp` = base field of Pallas = scalar field of Vesta, `p = 0x40000000000000000000000000000000224698fc094cf91b992d30ed00000001` (255 bits; `2^254 < p < 2^255`) |
| Commitment curve | Vesta (`Fq`-points over `Fp`... see below): polynomial commitments are to points of Vesta, whose scalar field is `Fp` |
| Embedded curve | Pallas: short Weierstrass `y² = x³ + 5` over `Fp`, prime order `q = 0x40000000000000000000000000000000224698fc0994a8dd8c46eb2100000001`, cofactor 1 |
| Scalars of Pallas | `Fq` elements; the protocol uses only scalars that are hash outputs in `Fp`, interpreted as integers (§3) |
| Public parameters | `Params::new(k)` of `halo2_proofs`: `2^k` generators of Vesta derived deterministically by hashing to the curve; nothing secret, nothing to trust, no ceremony |
| Circuit size | `k = 14` (`2^14` rows) for the transfer circuit of §8 |
| Proof encoding | the byte string of the Blake2b-transcript proof of one instance of the transfer circuit: **4 416 bytes**, fixed by the circuit and `k` |

(Vesta's own base field is `Fq`; the only role of Vesta here is to carry the
commitments of the proof system, and nothing of the protocol is written in
`Fq`.)

Field elements on the wire: **32-byte little-endian canonical** (`value < p`,
else reject).

Pallas points on the wire: **32-byte compressed**: `x` as 32-byte LE with bit
255 set to the least significant bit of `y` (the `pasta_curves` convention).
Decoding rejects `x ≥ p`, `x³ + 5` non-square, and the identity (all-zero
encoding). There is no subgroup check: the curve has prime order.

## 2. Hash functions (replaces `PROFILE.md` §2.1; §2.2 amended)

### 2.1 Poseidon

| Parameter | Value |
|---|---|
| Field | `Fp` |
| Width `t` | 3 (rate 2, capacity 1) |
| S-box | `x^5` |
| Full rounds `R_F` | 8 |
| Partial rounds `R_P` | 56 |
| Round constants, MDS | the `P128Pow5T3` instance of `halo2_gadgets` for the Pallas base field (generated by the Poseidon reference generator for `n = 255, t = 3, R_F = 8, R_P = 56`); pinned by the implementation and re-derived by a script as `scripts/poseidon_params_check.py` does for the paper profile |

Hash mode `PH_A(tag, x_1, …, x_n)`: the **constant-length sponge** of
`halo2_gadgets` (`ConstantLength<L>` with `L = n + 1`) over the message
`[tag, x_1, …, x_n]`:

```
L        = n + 1
state    = [0, 0, L · 2^64]                 # capacity element encodes L (halo2 domain)
absorb the message two elements per permutation, padding with 0 to a multiple of 2
output   = state[0] after the last permutation
```

This differs from the paper profile's mode (capacity initialised to
`n + 1` in `state[0]`): the variant uses the halo2 domain so that the
in-circuit hash is the gadget's hash unchanged. Tags are first elements,
as before. Every `PH` of `PROFILE.md` §3–§6 is `PH_A` here.

Tags (replaces the table of `PROFILE.md` §2.1): `tag = LE_int(ASCII)` as
`Fp` (labels ≤ 31 bytes), with the labels `sb-a/v1/node`, `sb-a/v1/leaf`,
`sb-a/v1/nf`, `sb-a/v1/rho`, `sb-a/v1/eph`, `sb-a/v1/sknf`, `sb-a/v1/vkin`,
`sb-a/v1/view`, `sb-a/v1/div`, `sb-a/v1/kdf`, `sb-a/v1/stream`,
`sb-a/v1/mac`, `sb-a/v1/aux`, `sb-a/v1/nflock` (the last two reserved for
the swap extension). Distinct from the paper profile's `sb/v1/…` labels
by construction.

### 2.2 Byte-oriented hashes

`H_body = SHA-256(const_salt ‖ body_bytes)`, then **clear bits 254 and
255** of the LE value, interpreted as `Fp` (`< 2^254 < p`; 254-bit
collision resistance). Everything else of `PROFILE.md` §2.2 unchanged.

## 3. Keys and addresses (amends `PROFILE.md` §3)

| Key | Derivation |
|---|---|
| `sk_master`, `vk_out` | unchanged (HKDF-SHA256, infos `sb-a/v1/master`, `sb-a/v1/out`) |
| `sk_spend` | `LE_int(HKDF-SHA256(ikm = sk_master, salt = "", info = "sb-a/v1/spend", L = 64)) mod p`, an `Fp` element; this is the circuit witness |
| `sk_nf` | `PH_A(T_SKNF, sk_spend)` ∈ `Fp` (in circuit) |
| `vk_in` | `PH_A(T_VKIN, sk_spend)` ∈ `Fp` (in circuit) |
| `sk_view` | `PH_A(T_VIEW, vk_in)` ∈ `Fp`, **used as a Pallas scalar** (in circuit) |

**Field elements as scalars.** A hash output `s ∈ Fp` is used as the
scalar `LE_int(s) ∈ Fq`; since `p < q` no reduction occurs and the map is
injective. `s = 0` is invalid (the point would be the identity); the
probability is `1/p`. In circuit the gadget's base-field-element scalar
multiplication is used (`halo2_gadgets` `ScalarVar::from_base`), as
Orchard does for `[ivk] g_d`. The paper profile's `Scalar250` truncation
disappears.

Diversified address for diversifier `d` (11 bytes): `G_d = DiversifyHash(d)`
(§4.2), `pk_d = [sk_view] G_d`, `addr = (d, pk_d)`; no cofactor step.
Diversifier selection unchanged with info `sb-a/v1/diversifier`.

Address text encoding: bech32m, payload `d (11) ‖ pk_d (32)`. HRP: `sba`
mainnet, `tsba` signet/testnet, `rsba` regtest. Viewing keys: `sbavk1…`,
`sbaovk1…`.

## 4. Group operations (replaces `PROFILE.md` §4)

### 4.1 Point validation

On-curve and not the identity (§1). No subgroup check, no cofactor
clearing anywhere: every `[8]·` of the paper profile is removed.

### 4.2 DiversifyHash

```
DiversifyHash(d):
    x  = PH_A(T_DIV, LE_int(d))                     # d as an 88-bit field element
    u  = x^3 + 5
    if u is not a square in Fp: return INVALID
    y  = sqrt(u) with y even (LSB = 0)              # canonical sign
    return (x, y)                                   # prime order: no cofactor
```

In circuit the prover witnesses `y`, the point is witnessed as a
non-identity curve point (the gadget checks the curve equation), `x` is
constrained equal to the hash output, and `y` is constrained even by
`y = 2h` with `h` range-checked below `2^254`. About half of all
diversifiers are invalid, as before.

## 5. Notes (amends `PROFILE.md` §5)

§5.1 unchanged with `Fp` in place of `Fr`; `rho = PH_A(T_RHO, rseed)`,
`sk_eph = PH_A(T_EPH, rseed)` used as a Pallas scalar (§3),
`pk_eph = [sk_eph] G_d`. §5.2 (recipient channel), §5.3 (leaf), §5.4
(nullifier) unchanged with `PH_A`, Pallas points and `Fp` elements; the
leaf's `h_aux = 0` as before.

## 6. Note tree (replaces `PROFILE.md` §6)

Append-only Merkle tree, depth **32**, nodes `PH_A(T_NODE, left, right)`,
empty leaf `0`, empty subtree roots `E_0 = 0`, `E_{i+1} = PH_A(T_NODE,
E_i, E_i)`. Positions and per-block roots as before.

## 7. Transfer envelope (amends `PROFILE.md` §7)

Arity fixed at **N = 2, M = 2** with dummy padding. Body bytes exactly as
`PROFILE.md` §7.1 with these substitutions:

| # | Field | Bytes | Change |
|---|---|---|---|
| 0 | `magic` | 3 | `"btc"` (unchanged) |
| 1 | `version` | 1 | **`0x02`** (family A) |
| 7 | `nf[0..2]` | 2 × 32 | `Fp` LE canonical |
| 8 | `pk_eph[0..2]` | 2 × 32 | compressed Pallas (§1) |
| 9 | `ct_note[0..2]` | 2 × 96 | three `Fp` each |
| 10 | `ct_out` | 176 | unchanged (ChaCha20-Poly1305, §7.3) |
| — | **body total** | **508** | unchanged |
| 11 | `proof` | **4 416** | Halo 2 proof, §1 |
| — | **envelope total** | **4 924** | |

`h_body = H_body(const_salt ‖ body_bytes)` (§2.2), proof bytes excluded as
before. The parser rejects a proof field of any other length. The paper
profile's indexer rejects version `0x02` as an unknown version
(`PROFILE.md` §11 step 1) and this profile's indexer rejects `0x01`.

## 8. Transfer statement and circuit (replaces `PROFILE.md` §8)

### 8.1 Public inputs

The 17 `Fp` elements in the order of `PROFILE.md` §8.1 (`const_salt`,
`r_anchor`, `N`, `M`, `nf_0`, `nf_1`, `pk_eph_0.x`, `pk_eph_0.y`,
`pk_eph_1.x`, `pk_eph_1.y`, `c_0^0`, `c_1^0`, `tag^0`, `c_0^1`, `c_1^1`,
`tag^1`, `h_body`), as one instance column.

### 8.2 Witness

As `PROFILE.md` §8.2 with `Fp` elements and Pallas points; additionally
the even `y` of each `G_d` and, for every input, `pk_d` as a witnessed
point constrained equal to `[sk_view] G_d` (the gadget's scalar
multiplication yields a possibly-identity point; equality with a
witnessed non-identity point gives the non-identity check).

### 8.3 Constraints (Appendix B blocks)

Blocks 1–8 of `PROFILE.md` §8.3 with these readings:

1. Derivations as there, `PH_A` throughout; `pk_d = [sk_view] G_d`,
   `pk_eph = [sk_eph] G_d`, `ss = [sk_eph] pk_d` by variable-base
   multiplication with base-field scalars.
2. The Merkle root equals `r_anchor` unless `v = 0`: `(root − r_anchor) · v = 0`.
3–5. As there.
6. `v` is 64-bit range-checked (six 10-bit lookups and a 4-bit check), `d`
   88-bit (eight lookups and an 8-bit check), `pos` is decomposed into 32
   constrained bits that also drive the Merkle path's swaps.
7. `v_in_0 + v_in_1 = v_out_0 + v_out_1` (one gate).
8. `h_body`, `N`, `M` are instance cells; `N` and `M` are constrained to
   the constants 2 and 2; `h_body` and `r_anchor` need no extra
   constraint in PLONKish (instance cells are bound by the permutation
   argument).

Arithmetization note: the circuit's gates, column layout (ten advice
columns, one instance column, eight fixed columns of which six carry
Poseidon round constants, one coefficient column, one 10-bit lookup
table) and chips (`halo2_gadgets` Poseidon `Pow5`, ECC, lookup range
check; own gates for the linear combinations, the bit decomposition,
the conditional swap, the dummy rule, the parity rule and the sum) are
those of `experiments/halo2-transfer`, which is the structural reference
of this section until the variant's `sba-circuit` crate exists.

Measured (`VARIANT-A.md` §4.2): `k = 14`, proof 4 416 bytes, proving
2.0 s, verification 24.5 ms (20 threads).

### 8.4 Verifying key

No key material is generated or distributed. The verifying key is a
deterministic function of the circuit and `k`; an implementation
derives it (`keygen_vk` over `Params::new(14)`) and a deployment profile
pins its identifier `vk_id`: the 32-byte LE encoding of the scalar
squeezed from a Blake2b transcript into which the verifying key was
hashed (`VerifyingKey::hash_into`, then one challenge). Two
implementations that derive different `vk_id` disagree on the circuit
and must not share a deployment.

## 10. Publication carrier (amends `PROFILE.md` §10 and `WITNESS-CARRIER.md`)

Both carriers are defined for the family with the envelope of §7:

* **Witness carrier (default).** As `WITNESS-CARRIER.md`: the envelope in
  a tapscript revealed by a script-path spend of a NUMS-keyed P2TR
  output. 4 924 bytes of envelope in 520-byte pushes; the pair weighs
  ≈ 153 + 1 350 ≈ 1 503 vB [computed, `VARIANT-A.md` §4.3].
* **OP_RETURN carrier.** As `PROFILE.md` §10 with a 4 924-byte push
  (`OP_PUSHDATA2`), ≈ 5 049 vB; permitted, not recommended.

A deployment names one carrier; the candidate rule, the exactly-one
rule and the rejection logging are those of the chosen carrier's
document.

## 11. Replay acceptance order (amends `PROFILE.md` §11)

Steps 1–5 and 7 unchanged. Step 6: **verify the Halo 2 proof** for the 17
instance values of §8.1 against the deployment's verifying key (§8.4),
else reject. An indexer may verify several proofs in one batch
(accumulation) provided the result is identical to verifying each
alone; acceptance is defined per envelope.

| 3-bit clearing of `h_body` | 2-bit clearing | `p > 2^254` |

## 13. Versioning (amends `PROFILE.md` §13)

The family's profile version is `a-MAJOR.MINOR` (this document's title,
`a-0.1`); its wire version byte is `0x02`. The rules of `PROFILE.md` §13
apply within the family: while the profile is a draft, every
incompatible change bumps MINOR and old envelopes are rejected; from
`a-1.0` on, changes bump the wire version byte. Family bytes are
assigned once: `0x01` the paper profile, `0x02` this family; later
families take the next values (`VARIANT-A.md` §6.2).

## 14. Security analysis: what the variant changes (new)

The paper's analysis (§17–§20) is inherited where it does not depend on
the proof system or the curve; the parts that do:

* **Knowledge soundness** (§19): Groth16's argument in the generic group
  model is replaced by Halo 2's: discrete logarithm on Pasta and the
  random-oracle model for the Fiat–Shamir transcript. No pairing, no
  q-type assumption, no setup trust.
* **Proof re-randomization** (§14.3): the known Groth16 re-randomization
  map does not exist for a Fiat–Shamir proof whose transcript includes
  the statement; non-malleability of Halo 2 proofs is nonetheless not
  proven, so the caveat is restated as "non-malleability unproven", and
  the defence (replay rejects a repeated nullifier) stands unchanged.
* **Trusted setup** (§8.4 of the paper profile, `CEREMONY.md`): void.
* **Verification cost**: 24.5 ms per proof against 4 ms (§8.3), linear in
  `2^k`; the indexer's replay throughput and the light-client sync of
  `REPLAY-PROOF.md` must be re-measured for the family.
* **Encryption and keys** (§12, §6): unchanged in design; the curve change
  does not alter the privacy argument (ECDH on a prime-order curve with
  a committing symmetric layer).
* **Not post-quantum**: `POST-QUANTUM.md` §1 applies in full.
